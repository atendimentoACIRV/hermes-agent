## Fork-owned workflow design

Use the existing fork-owned `workstation-ci.yml` and `workstation-browser-windows.yml` as the starting owners. Extend or consolidate those lanes for Stage A instead of restoring the upstream `ci.yaml` umbrella or calling inherited broad `tests.yml`, `tests-os.yml`, Nix, or Docker workflows. Add a separate fork-focused workflow only if those existing owners cannot express the required stable Stage A check without duplicating a lane. Keep one Windows owner for a given candidate/path set; tighten the Browser workflow's broad `workstation/**` trigger to native Browser-relevant paths only after mapping all required native contracts, and move expensive soak/package evidence to an explicit SHA-bound lane only where the corresponding acceptance gates still block promotion.

The automatic Stage A path should be a small, exact-head gate:

1. Run direct fork-owned checks on a standard Ubuntu runner, without an OS matrix or 32-core runner. Include repository code-health and the Workstation/durable contracts required by the candidate; use the repository test runner and the applicable focused suite. Bind the run to the PR head SHA and verify the checked-out `HEAD` equals the event SHA.
2. Keep the full native Windows qualification in one manually dispatched lane, with all 15 existing steps and their blocking final aggregate intact. Remove the `pull_request` trigger; require `candidate_sha` (exactly 40 hexadecimal characters) and a non-empty `qualification_reason`. Before any qualification step, validate the input and require it to equal `github.sha`; check out `github.sha` and assert `git rev-parse HEAD` equals that same SHA. Dispatch against the candidate branch/ref whose workflow revision is the same candidate. Never skip a required step or turn missing/skipped evidence into green.
3. Dispatch the full Windows lane once, after local candidate checks pass, whenever the change impacts native or packaged behavior. Record the exact candidate SHA, reason, workflow run/check URL, and all required passing results in the promotion receipt. Missing dispatch or receipt means **NOT QUALIFIED** and blocks promotion; manual means deliberately scheduled evidence, not optional evidence. If the 45-minute timeout is exceeded, preserve the run and profile evidence before deciding whether a targeted timeout adjustment is justified; do not blindly rerun.
4. Use narrow path applicability for each lane and include its workflow files and scripts in its own trigger scope. Keep one stable aggregate required check that waits for applicable required jobs and fails when a required lane is missing, skipped unexpectedly, or failed. A path-filtered workflow that never starts is not a green required check.
5. Cancel superseded PR runs by PR number/head concurrency group. Preserve main, release, and manually requested evidence; do not cancel a promotion run merely because another PR update arrived.
6. Grant `contents: read` by default; do not expose secrets or write credentials to PR-controlled code. Pin every third-party Action to a reviewed full commit SHA. Keep any write-capable publishing or automation in its separately protected release workflow.

Do not solve compute cost by weakening the checks needed for behavior, native, packaged, baseline, or exact-head claims. A change in cost or path applicability needs a recorded mapping from changed paths to the evidence still required by [TESTING.md](TESTING.md). Keep workflows from upstream available for review/history, but do not re-enable or invoke their broad automatic triggers in the fork as a shortcut.
